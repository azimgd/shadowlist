# Code style

One rule set for `shadowlist-core`, `shadowlist-fabric`, `shadowlist-uikit`, `shadowlist-appkit`, `shadowlist-android`, `shadowlist-wasm` and the apps in `templates/`. Where a language has its own idiom the table says so. Everything else is the same in every language.

## Naming

| What                          | C++                                | Objective-C                         | Swift                     | Kotlin                       | Java                            |
| ----------------------------- | ---------------------------------- | ----------------------------------- | ------------------------- | ---------------------------- | ------------------------------- |
| Types                         | `PascalCase`                       | `Prefix` + `PascalCase`             | `PascalCase`              | `Prefix` + `PascalCase`      | `Prefix` + `PascalCase`         |
| Functions, locals, parameters | `camelCase`                        | `camelCase`                         | `camelCase`               | `camelCase`                  | `camelCase`                     |

Class prefixes say which package a type lives in. Objective-C has one global namespace and the prefixes must never collide.

| Package                                                       | Prefix                                                                                                                                                                                                                        |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shadowlist-fabric`                                           | `ShadowList` for classes, `SL` for file-local helpers, macros and constants (`SL_SCROLL_TO_TOP_DURATION`)                                                                                                                     |
| `shadowlist-uikit`, `shadowlist-appkit`, `shadowlist-android` | `ShadowListKit` for every type, the Bench apps included. Objective-C constants take `SHADOWLIST_KIT_` (`SHADOWLIST_KIT_LIFT_DURATION`). Kotlin constants sit unprefixed in their class (`ShadowListKitCore.LIFT_DURATION_MS`) |
| `shadowlist-wasm`                                             | `ShadowListKit` for classes and types. The wasm exports are `<Class>_native<Name>` behind one `SHADOWLIST_KIT_WASM(name)` macro (`ShadowListKitCore_nativeRunPasses`), the rule shadowgrid-wasm follows                       |
| `shadowlist-core`                                             | namespace `azimgd::shadowlist`, no prefix. File-local helpers go in an anonymous namespace. Macros take `SHADOWLIST_` (`SHADOWLIST_LOG`, `SHADOWLIST_DEBUG_LOG`)                                                              |
| Runtime flags                                                 | `SL` + `PascalCase` (`-SLRoute`, `-SLEngine`, `-SLBench`, `SLCount`). One name on every platform. Never renamed                                                                                                               |

One word per concept in every language: `previous` (not `prev`, `old`, `last`), `current`, `index`, `count`, `offset`, `low` / `high` for an inclusive index range, `delete` (not `remove`), `anchor` for what MVCP holds in place, and `xDp` / `xPx` for units. The plural is always `indices`, never `indexes`. Framework parameter names (`oldProps`, `oldScrollX`) and trace log keys stay as they are. A leading `_` marks an unused JS binding, and names local to a macro take a prefix such as `slt_a`. Visible means any pixel on screen, viewable means past the threshold, and measured means the core's measured range (visible plus overscan). `window` alone is the OS window (`NSWindow`, `UIWindow`, Android's `Window`). Qualified it can mean two more things: the viewport's size (`windowAlong`, `windowCross`, `windowHeight`), or, always as `row window` or `column window`, a slice of rows or columns a host keeps loaded (`ROW_WINDOW`, `moveRowWindowToRow`).

A size with no unit in its name is a logical size: points on iOS and macOS, dp on Android, CSS pixels on the web. They are the same length at zoom 1, so the wasm docs say CSS pixels where the native docs and the Fabric specs say points, and the same rule holds in shadowgrid. A size in device pixels is named `xPx`.

## Words across shadowlist and shadowgrid

shadowgrid draws on shadowlist, so one call stack holds both repos' words with different meanings. Read them by
layer. This section is the same in both repos' `docs/code-style.md`; change it in both.

| shadowgrid                                | shadowlist                                       |
| ----------------------------------------- | ------------------------------------------------ |
| `row`, one line of the grid's data        | `item`, one entry of the list's data             |
| a display row, a row's place after sort   | `row`, a placed slot in the list's layout        |
| `cell`, one row and one column, its value | none: a list `cell` is the view that shows a row |
| `key`, a row's identity across updates    | `key`, an item's or row's identity               |

## Public API words

Four nouns, the same in every layer:

- `item`: one entry of the user's data. The only data word in public API, and its index is the item index.
- `row`: one placed slot in the layout, an item or a section header or footer row. Core, host and internals only. In a plain list the row index equals the item index.
- `cell`: the view that shows a row (`ShadowListKitListCell`, Fabric `ShadowListCellView`).
- `key`: stable identity of an item or row. Never `id`.

Every platform uses the same word for each concept and only changes the shape to fit its language. Fabric keeps React Native's name where FlatList, SectionList or ScrollView define one (`renderItem`, `initialNumToRender`, `scrollToIndex`, `ListHeaderComponent`). `shadowlist-wasm` uses the Kotlin column for the parts it has.

- A new public concept gets one row here before it ships on any platform.
- A rename is a hard break: no alias and a minor version bump.

Codegen specs, the same in shadowlist and shadowgrid:

- A native event's payload type is `<Name>Event` (`DragEndEvent` for `onDragEnd`), or `Native<Name>Event` where the public API already wraps one under that name (`NativeScrollEvent` in `ScrollEvent`). Payload types stay out of the package index.
- Row and column indices cross as `Int32`, as do counts of rows and columns. `Double` is only for a count that can pass 2^31, and its comment says so.
- A callback for a state that changed is `on<State>Change` with one event object, in the present tense. Names a library takes from an upstream API keep the upstream form: FlatList's `onViewableItemsChanged`, AG Grid's `onXChanged` on DataGrid.
- A call the library cannot carry out, such as a scroll to a row that is not there, tells the caller through a callback where it can recover (FlatList's `onScrollToIndexFailed`), and otherwise warns in development and does nothing. Only an API that is declared and not implemented throws, in development.

## C++

- `#pragma once` in every header, including the Objective-C++ headers in `shadowlist-fabric`.
- Indices are `std::size_t`, and `UNDEFINED_INDEX` means "no index". Don't use `long` or `-1`. Convert to a signed type only inside the arithmetic that needs it.
- Platform edges convert the missing index: `UNDEFINED_INDEX` ↔ `-1` in JNI, `UNDEFINED_INDEX` ↔ `NSNotFound` in Objective-C.
- Commit tokens are `std::uint64_t` in C++. A bridge that carries one in a `double` slot converts at the JNI or Objective-C boundary.
- Write `this->` only when a name is shadowed.
- Pass a non-null `Container` as `Container&`. A raw pointer always means non-owning and nullable.
- Mark classes that aren't designed for subclassing `final`. Plain data stays a `struct` with public fields.
- Constants are namespace-scope `constexpr` unless only one class reads them.
- Write references as `const T& name`, in core and in Objective-C++ alike.
- Includes come in this order: the file's own header, a blank line, `<shadowlist-core/...>` sorted, a blank line, then std headers sorted. Tests put their quoted local headers first.
- Each parameter goes on its own line once a signature passes 120 columns.
- Leave unused parameters unnamed (`JNIEnv*, jclass`, `const std::string&`).
- Callbacks stored in a member are `std::function` named for what they give (`measureRow_`, `snapOffset_`). Helpers in headers take template callables.

## Core tests

- Every change in `packages/shadowlist-core` comes with a test in `packages/shadowlist-core-tests`.
- Test names are sentences in `snake_case` that state the behavior: `TEST(a_prediction_for_a_live_row_reflows_the_rows_after_it)`.
- Put the test in the `tests_*.cpp` file of its area. Host layer tests go in `tests_host_*.cpp`.

## Objective-C and Swift

- Headers sit inside `NS_ASSUME_NONNULL_BEGIN/END` and mark nullable values with `nullable`.
- Private headers are `Class+Private.h`.
- Allocate with `[X new]` when there are no arguments. Check for nil with `!_x` / `_x`. A pointer turned into a `BOOL` keeps `_x != nil`.
- Inside the class, read ivars directly (`_horizontal`), not through `self.`.
- C++ engine objects are value ivars. Lambdas that call back into Objective-C capture `weakSelf`.
- Constants are `static const` with the package prefix: `SL_X` in Fabric, `SHADOWLIST_KIT_X` in the kit. Durations are in seconds.
- Split files into sections with `#pragma mark - Name`.

## Kotlin and Java

- Kotlin for new Android code. Fabric's Java stays Java until a file is rewritten.
- Methods declared `external` / `native` are named `native*` and are `private`. A public or internal wrapper calls them with the handle.
- Durations are `Long` constants in milliseconds with an `_MS` suffix (`LIFT_DURATION_MS`). Dp values take `_DP`.
- Mark sections with `// region Name` and close them with `// endregion`. Use `@Nullable` in Java and `T?` in Kotlin. Library code never uses `!!`.

## JNI

- The C++ object behind a handle is `struct Peer`, found with `peerOf(jlong handle)`.
- The field holding it is `handle` in Kotlin and `mHandle` in Java. `destroy()` frees the peer and sets the handle to 0.
- The owner calls `destroy()` when its view detaches or is dropped. The next use creates a new peer lazily.
- Entry points sit in one `extern "C"` block and use one macro per class (`SHADOWLIST_KIT_JNI(name)`, `SL_SCROLL_SYNC_JNI(name)`).
- Includes: `<jni.h>` first, then std headers, then core headers.
- Slot arrays mirror a named enum on both sides (`PASS_*`, `STICKY_*`). Never index them with bare numbers. What the JNI and wasm bridges share, the pass slots, the commit flags and the checked conversions of numbers into core enums, sits once in `packages/shadowlist-core/host/KitBridge.hpp`.

## Kits

`shadowlist-uikit` and `shadowlist-android` are one design in two languages. A change in one kit lands in the other in the same change with the same names, or the change notes why not.

`shadowlist-appkit` is the UIKit kit on AppKit with the same class names, selectors, category files and comment wording. Where a feature exists on both it keeps the UIKit selector. It adds what the Mac needs and the other kits have no counterpart for yet: `ShadowListKitScrollEngine` and `ShadowListKitScrollerView` with their `+Scrolling` category, driven mode, keyboard selection, type select, activation, hover, the swipe actions as a menu and as accessibility custom actions, and reorder accessibility actions. It leaves out pull to refresh, the section index, `editing` on the list and UIScrollView's keyboard insets and scroll to top. The [AppKit README](../packages/shadowlist-appkit/README.md#differences-from-the-uikit-kit) keeps that list.

`shadowlist-wasm` is the same design in TypeScript for the parts it has. Its classes, sections and helpers carry the Android kit's names, and `cpp/ShadowListKitCoreWasm.cpp` follows the JNI rules: a `Peer` found with `peerOf(handle)`, `native*` entry points in one `extern "C"` block behind `SHADOWLIST_KIT_WASM(name)`, and slot enums mirrored in `ShadowListKitCore.ts`. TypeScript marks sections with `// region Name` and `// endregion`.

- `ShadowListKitListView` sections come in this order on both: Axis, Properties, Cells, Data, Sections, Layout, Mounting, Prefetching, Measurement, Separators, Events, Selection, Scroll events, Queries, Saved position, Accessibility, Scroll commands.
- iOS puts Data, Sections, Selection, Saved position with Scroll commands, Accessibility, Drag, and swipe actions with menus in category files (`ShadowListKitListView+Data.mm`, `+Sections`, `+Selection`, `+Commands`, `+Accessibility`, `+Drag`, `+Actions`). The layout pass both Apple kits run, with its Cells, Layout, Sticky, Mounting, Prefetching, Measurement, Separators, Events and Queries sections in that order, sits in `+Passes`, and each kit's `ShadowListKitListView.mm` keeps the rest of those sections. Android keeps them as regions of `ShadowListKitListView.kt` or in its controllers (`ShadowListKitDragController`, `ShadowListKitSwipeController`).
- Platform-only sections stay where they are: List and Delegate on iOS. List and Environment on the Mac. Drawing order, Edges, Nested scrolling and Drag on Android.
- Files both Apple kits share live in the UIKit kit, and the AppKit kit links them with relative symlinks. A shared file imports only shared headers, by their path relative to it. CocoaPods compiles a linked file from the UIKit folder, where a relative import finds the UIKit kit's headers. What differs sits behind `TARGET_OS_OSX` in the shared file or in a helper in `ShadowListKitPlatform.h` (`ShadowListKitLayoutNow`). Each kit keeps a file of its own where most of it is platform code. The [AppKit README](../packages/shadowlist-appkit/README.md#layout) lists the shared files.
- The Mac's `+Testing.h` keeps the UIKit categories for what both kits drive, `(DragTesting)` and `(ActionsTesting)`, and adds `(Testing)` for scrolling, `(SelectionTesting)` and `(AccessibilityTesting)`.
- Tests: the AppKit kit's in `packages/shadowlist-appkit/Tests` with `swift test`, the Android kit's in `ShadowListKit/src/androidTest` on a device. The UIKit kit has its Bench and example app, and the AppKit kit has no Bench yet.
- Drag files use Pick up, Follow, Drop. Text files use Layout, View: the Apple kits share the layout in `ShadowListKitTextLayout.mm` and keep the view in `ShadowListKitText.mm`.
- Lifecycle teardown sits next to init: `dealloc` on iOS, `onDetachedFromWindow` on Android.
- Helpers share names: `mountRow`, `recycleStaleCells`, `mountPlan`, `mountedCell`, `unpinCell`, `stopScrolling`, `runCommandNow`, `hasHeldRow`, and the `previousOffset` field.
- Drag math, timers and state machines live in the core's `host/DragReorder` and `host/DragBoard`: placing the held row, the drop spot and shifts, edge scroll speed per second, the press slop, the haptic tick spacing, the wait for a drop to land and a drag board's flight. Hosts keep the views, the gestures, the animations and the hit test, and read every shared number from there.
- A value both kits use lives once in `packages/shadowlist-core/host` as a `constexpr` in milliseconds (`DRAG_DROP_DURATION_MS`). iOS converts it to seconds (`SHADOWLIST_KIT_DROP_DURATION = DRAG_DROP_DURATION_MS / 1000.0`), and Android reads it through JNI (`ShadowListKitCore.DROP_DURATION_MS`).
- Other constants share names: iOS `SHADOWLIST_KIT_X` in seconds, Android `X_MS` in milliseconds.
- Scroll commands call `stopScrolling` (stop momentum and cancel the landing) before they send the command to the core.
- The same logic carries the same comment wording in both kits.
- Android plans mounts over the frames it copied from the core, the same rule as `ListDriver::planMount` and `ListDriver::shouldMount`, because a scroll frame there makes no JNI call for it. iOS and the web call the driver's `planMount`. The core test `list_driver_mount_plan_reaches_into_the_insets` holds the rule.
- A saved position lands through `ListDriver::restoreAnchorState` in every kit, and waits while the data lacks its key. Then iOS invalidates the frame for UIKit's next layout, and Android and the web lay out right away through `runCommandNow`.

## Comments

Comments are short narration of what happens, not explanations of how. A comment longer than one line, or any comment above a declaration, is a `/* */` block with one `*` per line. A one-line comment inside a body stays `//`. Interface and type blocks carry no comments: TypeScript `interface` and `type` bodies and Objective-C `@interface` blocks list members only. What a member means goes in the block above the declaration, and the class doc goes in one block above the `@interface`. Contracts the user implements, Objective-C `@protocol` and Kotlin `interface` bodies such as the data source and delegate, keep a block above each method that needs one. A method its name explains goes without, and related methods, like the section calls, share one block above the group. Delete a comment when the code already says it. Avoid the "X, so Y" pattern in comments and docs: split it into two sentences, write "Y because X", or drop the clause. No `--` or em dash asides: make the aside its own sentence or drop it.

## Structure

New code follows the file and siblings it lives next to: include and import order, initializer style, file layout and export style. TypeScript imports come in this order: `react`, `react-native`, other packages, then relative imports, with one import statement per module. `local/import-order` and `no-duplicate-imports` in `eslint.config.mjs` check it. Shared logic goes in `packages/shadowlist-core/host`, and the iOS, Android and Fabric adapters call it rather than copying it. Unused code is deleted, not commented out.

Use named constants, never bare numbers for event types or slots. Enums mirrored across C++, Objective-C, Kotlin and Java, such as out slots and state keys, keep the same names and numbers. Removing a feature removes its docs, package entries, trace macros, includes and test helpers too.

## Repo

- Edit `packages/shadowlist-core` only, never its mirror in `shadowlist-fabric`.
- Example apps, demo screens and ShadowListUtils live in `templates/`.
- Commits are a single conventional line such as `fix:` or `refactor:`.

## Checklist before you finish

- Core changed: a new test, and `yarn test:core` passes. CI runs the core tests under ThreadSanitizer too.
- Kit changed: the other kit has the same change, and both kit example apps build.
- Wasm changed: `yarn build:wasm` and `yarn test:wasm` pass.
- Fabric or JS changed: `yarn typecheck`, `yarn test` and `yarn lint` pass.
- Always: `yarn format:check` and `yarn docs:check` pass, as CI checks both.
- A new or renamed public word has its row in the Public API words table.
- Comments follow the block rules and no `@interface` or TS `interface` / `type` body has one.
- No "X, so Y" and no `--` asides in new comments, docs or commit messages.
